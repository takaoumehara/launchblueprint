# AI向け：Tech Catalog の使い方

このカタログは、技術の提案を**記憶ではなく記録から**出すためにある。記憶で書いた価格や制限は、去年の値かもしれない。Stripe Connect の方式で責任の所在が変わると、作ってから気づいたプロジェクトがあった。その種の見落としを、提案する前に止めるのが目的。

## 技術を提案する時（毎回この順で）
1. `project.blueprint.yaml` を読む。`selected` と `rejected` とその理由、`rules` を確認する。`rejected` を理由なしに再提案しない。
2. 該当ドメインの YAML を全エントリ読む。1つだけ読んで決めない。
3. 候補を2〜3つに絞り、比較カード（v3 §8）で出す。各カードに `pricing_bands` の4帯を全部書く。オーナーが「無料」と言っていても、$5〜$10帯で何が増えるかを書く（それは好みであり、ルールではない。§9）。
4. `lock_in` が「高」か「変更不可」なら、カードの一番上に書く。
5. `liability_compliance` に責任の移動があれば、先回りリスク調査（§7）に1行足す。
6. **鮮度はフィールドごと**に判定する（`freshness.yaml`：security 7日・規制/対応状況/limits 30日・料金 90日・考え方 180日）。`source.verified: false` または `checked: null` は「未確認」。古い・未確認の数字を使う時は公式ページで確かめてから書く。確かめられなければ「未確認」と書いて出す。**selected の item から先に**出す。
7. おすすめは1つだけ。「この企画では、なぜこれか」を1〜2文で書く。

## 読むファイル（この順）
1. `project.blueprint.yaml`（選択と理由） 2. `rules.yaml`（ルール本文・強さ・review_due） 3. `freshness.yaml` 4. 該当ドメインの YAML 5. `build_vs_buy.yaml`（作る／API／全部入りの比較が要る時） 6. `blueprint-v3.md`（手順の背景）

## 答え方の型
- 出典は「ファイル ＋ item id ＋ URL ＋ checked 日付」。ルールは id と本文を両方書く。
- **後戻りできるか**を分けて書く：「変更不可（作り直し）」は item の `lock_in` / `liability_compliance` に書いてあるものだけ。推測で「変更不可」と書かない。
- 数字の計算は式を1行で見せる（例：3社 ×（$1.15＋$1.50）＝$7.95）。
- カタログに無いことは「カタログに無い」と書き、推測で埋めない。

## カタログを直す時
- 公式ページで確かめた値だけ `verified: true` にし、`checked` を今日にする。
- 新しいサービスを足す時は schema.md の必須キーを全部埋める。埋まらないキーは「要確認」と書く。
- **直接書き換えない。** `catalog/proposals/YYYY-MM-DD-<id>.md` に「何を・なぜ・出典」を書いて、レビュー（v3 §15）を通す。
- IDは変えない。消す時は `deprecated: true` と後継IDを書く。

## オーナーと相談する時
- 「これに変えたい」と言われたら、まず影響ビュー（§11）を出す：どの選択が変わるか、増える月額、変わる責任、ぶつかるルール。
- 選択を変えたら `project.blueprint.yaml` の status と reason を書き換え、古い選択は `rejected`（理由：オーナーが変更、日付）として残す。
- 調べても分からないことは、推測で埋めずに「未確認の質問」にまとめて一度に聞く。

## やってはいけないこと
- 1つのサービスだけ調べて決める
- 無料の帯だけ調べる
- 記憶の価格を確認済みのように書く
- 会話の一言から、新しい除外ルールを黙って作る（ルール台帳に「要確認」で出す）

## 機械向けの入口（v3）
- まず `llms.txt` を読む。画面と同じデータは `data/*.json`（各ファイルの `meta.sources` が元の YAML、`meta.how_to_read` がこのファイル）。
- HTML 画面にも同じ JSON が `script#bp-data` に入っている。値は画面ではなく JSON／YAML から読む。
