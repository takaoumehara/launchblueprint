# UI/UX learnings (v2)

Generic UI/UX rules. The first set was learned while iterating on a mobile-first page editor (Oct 2026); the rest encode standard practice (WCAG 2.2 AA, platform guidelines, Core Web Vitals) so that every screen has a rule for accessibility, states, dark mode, motion, forms, touch, performance and i18n. Each rule maps one-to-one to `catalog/ui_ux.yaml` (same id) and has four parts: the **principle**, what to *avoid*, *why*, and a yes/no *check* for the requirements, design and QA gates. The machine-readable `check` and `phase` fields are what the MCP `ui_ux_checklist` tool returns. Phase gates per lifecycle stage are at the end.

Terms used here (token, component map, capsule, state switcher, skeleton, live region, safe area, Core Web Vitals, pseudo-locale, ...) are defined for non-engineers in `elements/glossary.yaml`.

## Emphasis and hierarchy

- **primary-action-color**: Reserve the strongest colour (solid black or brand fill) for the single primary action on a screen. *Avoid:* Several solid dark boxes and selected states all competing with the primary button. *Why:* Users' eyes were pulled between the main action and selected options, so the main action stopped standing out. *Check:* Is the strongest fill used by exactly one action on this screen?
- **selected-state-tint**: Show selected states with a light accent tint plus a thin ring, not a solid fill. *Avoid:* Selected chips filled solid in the same weight as the primary button. *Why:* A solid selected option looked like a second primary action. *Check:* Are selected states a light tint plus a thin ring, lighter than the primary action?
- **borders-only-on-pressables**: Use boxes and borders only for pressable buttons; use plain text links elsewhere. *Avoid:* Bordered boxes around labels, lists and secondary links. *Why:* Too many framed boxes made the header feel busy and hid what was actually tappable. *Check:* Does every bordered or boxed element respond to a tap?
- **never-red-for-success**: Never use red for a success state. *Avoid:* Red or warning colours on a successful state. *Why:* A success state in red read as an error. *Check:* Are all success states free of red?
- **plain-screen-labels**: Screen-name labels are plain text, and mode toggles state what they switch between. *Avoid:* Heavy black banner for a mode label; ambiguous toggles like 'Test links'. *Why:* A heavy preview banner looked ugly and an unclear toggle confused users. *Check:* Is the screen label plain text, and does every toggle name both states (e.g. 'Links: Edit / Open')?
- **icon-only-secondary-on-narrow**: On narrow screens, collapse secondary header actions to labelled icons (accessible name, 44px target) before squeezing the title. *Avoid:* Text labels on every header button so a short title wraps into two cramped lines. *Why:* Short titles wrapped needlessly because secondary buttons took the space. *Check:* At 390px, does a short title fit on one line, and do icon-only buttons keep an accessible name and a 44px target?
- **selected-vs-primary-color**: Keep selected states visibly lighter than the primary action, and draw focus rings in the brand colour at 3:1 or more. *Avoid:* Selected chips, focus rings and the primary button sharing one solid fill, or rings left in an old accent. *Why:* Selected options were mistaken for buttons, and old-accent rings looked like a different product. *Check:* Are selected states a tint, the primary action a fill, and focus rings brand-coloured at 3:1 or more?

## Copy and terminology

- **short-scannable-copy**: Keep UI copy extremely short and scannable. *Avoid:* Sentences in buttons, labels and toasts. *Why:* Long labels were truncated or skipped, and users missed the point. *Check:* Can every label and toast be read in one glance (a few words)?
- **plain-localized-terms**: Use plain, recognizable terms, localized to each locale's natural word. *Avoid:* Invented feature names or literal translations (e.g. 'Contents at the top'). *Why:* An invented label was not recognized; the standard term ('Table of contents') was. *Check:* Is each term the one users already know, translated to the locale's natural term?
- **no-ellipsis-truncation**: Never truncate text with an ellipsis; wrap, shorten copy or resize. *Avoid:* Labels cut off with '…'. *Why:* Cut-off labels hid meaning and looked broken. *Check:* Is there no text ending in '…' at the narrowest supported width (e.g. 360px) in every locale?
- **header-title-wraps-to-own-row**: Let a header title wrap (a few lines at most) or move to its own full-width row; never cut it off. *Avoid:* A page title truncated with an ellipsis or squeezed to one word per line beside header buttons. *Why:* People could not tell which page they were editing, and truncated titles looked broken. *Check:* At the narrowest supported width, is the full title readable in the header without an ellipsis?
- **one-term-per-concept**: Keep a product glossary and use exactly one term per concept across UI, help, emails and code (e.g. always 'page', never also 'site' or 'board' for the same thing). *Avoid:* The same object called 'page' in the editor, 'site' in settings and 'board' in the help centre. *Why:* Every extra name for one thing is a new concept users must learn, and support has to translate between them. *Check:* Does every screen, email and help page use the glossary term for each concept, with no second name in use? *See also:* plain-localized-terms, elements/glossary.yaml

## Guidance and discovery

- **hints-on-demand**: Keep hints off the main surface; put them behind an (i) or a one-time dismissible tip. *Avoid:* Always-on helper lines and tour buttons in section headers. *Why:* Permanent helper text cluttered the header and was ignored after the first visit. *Check:* Is every explanatory hint behind an (i) or shown once and dismissible?
- **announce-new-features-once**: Announce a new feature to all users, existing ones included, once, then never again. *Avoid:* Shipping an interaction change silently, or showing the tip on every visit. *Why:* Existing users never discovered a new gesture because only new sign-ups saw guidance. *Check:* Will existing users see one dismissible notice for this change, and only once?
- **distinct-coachmarks**: Make tour coachmarks visually distinct from the highlighted UI (dark bubble plus accent outline) with Back, swipe and progress dots. *Avoid:* A coachmark styled like the UI it points to, forward-only. *Why:* Users confused the tour bubble with the real control and could not go back. *Check:* Is the coachmark clearly different from the UI, and can users go back, swipe and see progress?
- **scoped-help-assistant**: An in-product help assistant answers only from the help content, cites the source page, links to screens instead of acting, and politely declines off-topic questions. *Avoid:* A general chatbot that answers anything or takes account actions. *Why:* Off-topic answers and unsourced replies erode trust. *Check:* Does the assistant refuse off-topic questions and cite a help page for each answer?

## Lists and editing

- **undoable-delete**: Delete immediately with an Undo toast, and offer Hide as a non-destructive alternative. *Avoid:* Blocking confirm sheet saying 'This can't be undone'. *Why:* Users feared deleting and asked why it could not be undone and whether they could just hide it. *Check:* Can a delete be undone from a toast, and is Hide offered?
- **handle-only-reorder**: Use a drag handle alone for reorder; put Move up/down in the overflow menu. *Avoid:* Drag handle plus up/down arrows plus overflow on every row. *Why:* Rows with three reorder affordances looked cluttered and redundant. *Check:* Does each row have only one visible reorder affordance?
- **no-overlapping-inserters**: Do not put between-item inserter buttons where they overlap content; use one Add button and 'Add below' in the overflow. *Avoid:* Floating '+' between list items. *Why:* The between-item '+' overlapped neighbouring items and kept drawing complaints. *Check:* Is there no insert control that overlaps or crowds list items?
- **preserve-scroll-highlight**: After closing an editor, return to the same scroll position and briefly highlight the edited item. *Avoid:* Jumping back to the top of the list. *Why:* Users lost their place after every edit. *Check:* After closing an editor, is scroll preserved and the edited item highlighted?
- **separate-preview-from-edit**: Separate an inline preview clearly from the edit list (Edit/Preview switch, framed and labelled preview). *Avoid:* Preview rendered inline with the same images as the list, with no boundary. *Why:* Users saw the same images twice and could not tell preview from editor. *Check:* Is the preview visibly framed or labelled, or switched separately from the edit list?
- **full-focus-edit-mode**: Item edit mode is full focus; define a show/hide matrix of controls per mode. *Avoid:* Global actions, Publish and add bars still visible while editing one item. *Why:* Mixed global and local controls made editing mode feel unclear. *Check:* Is there a written matrix of what shows in each mode, and does edit mode hide global actions?
- **tap-row-to-open**: Tapping a list row opens it; the row shows only its name and an overflow menu. *Avoid:* An extra Edit button on every row. *Why:* Per-row Edit buttons added noise without adding capability. *Check:* Does tapping a row open it, with no redundant Edit button?
- **collapse-long-nav**: Long in-page navigation collapses ('Contents ▾', '+N more') instead of growing without limit. *Avoid:* An ever-growing list of links at the top of long pages. *Why:* Long tables of contents pushed content below the fold. *Check:* Does in-page navigation stay short on long pages?

## Saving, settings and feedback

- **celebrate-publish**: Show publish success in clear green with a live message, Copy/Share actions and a small first-time celebration. *Avoid:* Neutral or ambiguous publish feedback. *Why:* Users were unsure whether their page had gone live. *Check:* After publishing, is success obvious, with copy/share right there?
- **sticky-save-bar-when-dirty**: Manual-save screens use a sticky bottom Cancel/Save bar that appears only when there are changes, the same on every manual-save screen. *Avoid:* Save and cancel as heavy boxes in the header, always visible. *Why:* An always-on header Save made three heavy boxes and gave no sense of unsaved changes. *Check:* Does the Save bar appear only when dirty, at the bottom, consistently across screens?
- **prevent-invalid-input**: Prevent invalid input by auto-adjusting (e.g. accent contrast) with Undo instead of showing an error. *Avoid:* Error message after the user picks an unreadable colour. *Why:* Users hit a contrast error with no idea how to fix it. *Check:* Is invalid input corrected automatically with an Undo, rather than blocked by an error?
- **separate-concepts**: Keep separate concepts in separate controls (publish status vs audience/visibility). *Avoid:* A 'Private' visibility option that overlaps with draft/unpublished state. *Why:* Users could not tell 'private' from 'not published'. *Check:* Does each setting control one concept, with no overlap between options?
- **consistent-save-model**: Make the save model explicit per surface (auto-saved to draft vs live at once vs manual) and show a consistent indicator. *Avoid:* Some settings live instantly, others draft, others manual, all looking the same. *Why:* An audit found mixed save behaviours that users could not predict. *Check:* For every control, is it obvious whether a change is drafted, live or needs saving?
- **toast-never-covers-controls**: Show transient messages in their own reserved space (above a bottom bar, clear of the safe area), never on top of tappable controls. *Avoid:* A floating toast laid over list items and buttons near the bottom of the screen. *Why:* A toast covered a button users were about to tap, so taps were missed or hit the toast. *Check:* While a toast is visible, is every control on screen still fully visible and tappable?

## Forms and input

- **time-inputs-for-novices**: Date/time inputs offer a 12h/24h toggle, prefill End from Start, label optional fields consistently, and explain inline when blank means unlimited. *Avoid:* Bare time fields where End starts empty, optional markers vary, and blank's meaning is undocumented. *Why:* First-time users had to guess formats and what an empty field meant. *Check:* Can a first-time user fill every time field without guessing? *See also:* prevent-invalid-input
- **irreversible-actions-name-consequence**: When an action truly cannot be undone (delete account, send money, publish to an audience), the confirmation names the object and the consequence; type-to-confirm is reserved for the most destructive actions; everything else is undoable instead of confirmed. *Avoid:* A generic 'Are you sure?' on every action, or a one-tap permanent account deletion. *Why:* Generic confirmations get clicked through by reflex, and then the one that mattered is gone. *Check:* Does every irreversible action name what will be lost, and does every reversible action skip the confirmation in favour of Undo? *See also:* undoable-delete
- **form-labels-always-visible**: Every field has a visible label that stays while typing and is linked to the input; placeholders show an example, not the label; mark only the minority of fields (optional or required) and do it the same way everywhere; help text sits under the field. *Avoid:* Placeholder-only labels that disappear on focus, asterisks on some screens and '(optional)' on others. *Why:* Once a placeholder disappears people forget what the field was for, and inconsistent markers make users re-read every form. *Check:* Does every input have a visible, linked label that remains while typing, and are required or optional markers identical across screens? *See also:* time-inputs-for-novices, a11y-accessible-names
- **form-validation-timing**: Validate a field when the user leaves it or submits, not on every keystroke before they finish; show the error next to the field in words that say how to fix it; keep the input; on submit, move focus to the first error and summarise when there are several. *Avoid:* 'Invalid email' shown after the first letter, errors only at the top of the page, and a submit that clears the form. *Why:* Premature errors feel like being scolded mid-sentence, and errors far from the field are missed. *Check:* Does an error appear only after the user leaves the field or submits, next to the field, in fix-it language, and does focus move to the first error? *See also:* prevent-invalid-input, error-state-recoverable, a11y-announce-changes
- **form-input-types-and-autofill**: Use the right input type, inputmode and autocomplete for every field (email, tel, one-time code, postal code, name, card) so the right keyboard and browser autofill appear; accept pasted and formatted input (spaces in card numbers, dashes in phone numbers); never block paste. *Avoid:* type=text for everything, onPaste preventDefault on the password field, and a card field that rejects spaces. *Why:* Typing on a phone is the slowest part of any form; autofill and the right keyboard cut it in half. *Check:* Does the right keyboard appear on a phone for each field, does browser autofill fill the form, and does pasting a formatted value succeed? *See also:* form-labels-always-visible, touch-targets-and-spacing
- **form-submit-once-with-feedback**: A submit button shows a busy state and ignores repeated taps while the request is in flight; it is disabled only during the request, not until the form is 'valid'; Enter submits a single-field form; the result (success or failure) is shown where the user is looking. *Avoid:* A button greyed out with no explanation until every field is right, or a double tap that creates two orders. *Why:* A disabled button gives no clue what is wrong, and double submissions create duplicate records and charges. *Check:* Can a double tap create two records, does the button show it is working, and can the user press Submit at any time to see what is missing? *See also:* error-state-recoverable, perf-respond-within-100ms
- **long-forms-keep-progress**: Forms longer than one screen show the steps, let the user go back without losing anything, and keep a draft across reload and navigation; only ask what is needed now and mark where the rest will be asked later. *Avoid:* A ten-field sign-up on one page, or a wizard where Back empties the previous step. *Why:* Every lost answer is a reason to abandon, and sign-up is where most users are lost. *Check:* After going back a step, reloading or leaving and returning, is every entered value still there, and can the user see how many steps remain? *See also:* consistent-save-model, external-setup-roundtrip

## Empty, loading, error and offline states

- **define-every-screen-state**: Design every screen and reusable component in all of its states before building: loading, empty (first use), empty (no results for a filter), error, offline or stale, partial, and populated with both 1 item and very many; record them in a screen × state matrix. *Avoid:* Designing and reviewing only the populated happy path, then letting the first user meet a blank or broken screen. *Why:* Most users meet the empty and error states first, and those are the states nobody designed. *Check:* Does the screen × state matrix list every state for this screen with a design each, and has each been seen in the running product? *See also:* empty-state-teaches-next-step, error-state-recoverable, loading-without-layout-shift
- **empty-state-teaches-next-step**: An empty state says what will appear here, why it is empty, and offers the one action that fills it; a no-results state offers to clear the filter or search. *Avoid:* A blank area, or 'No data' with nothing to do next. *Why:* First-use empty states are the onboarding most people actually see; a blank screen reads as broken. *Check:* Does every empty state have a one-line explanation and a primary next action, and does every no-results state offer to clear the filter? *See also:* define-every-screen-state, short-scannable-copy
- **loading-without-layout-shift**: Loading states reserve the final layout (skeletons or fixed sizes) so nothing already on screen moves when content arrives; show a spinner only for waits longer than a few hundred milliseconds and only in the area that is loading. *Avoid:* A full-page spinner for a partial reload, content that jumps down when an image or banner arrives, and a spinner that flashes for 50 ms. *Why:* Shifting content makes people tap the wrong thing, and flashing spinners make a fast app feel slow. *Check:* Does content appear without moving anything already on screen, and is no loading indicator shown for waits shorter than a few hundred milliseconds? *See also:* perf-images-and-media, perf-core-web-vitals-budget
- **error-state-recoverable**: Every error says what happened in plain words, what the user can do, and offers Retry or a way out; it keeps the user's input, and never shows raw codes or stack traces (log those with a reference id instead). *Avoid:* 'Something went wrong' with no action, a raw 'TypeError: undefined', or a form that empties itself after a failed submit. *Why:* Users judge a product by how it fails; an unrecoverable error loses both the work and the trust. *Check:* Can a user recover from every error without reloading or losing input, and does no screen ever show a raw error message or code? *See also:* define-every-screen-state, form-validation-timing, single-status-location
- **offline-and-stale-shown-once**: Detect offline and failed sync, show it in one place, label stale data instead of hiding it, and either queue writes with a visible pending state or disable them with a reason; never lose a write silently. *Avoid:* A blank screen with no network, a Save that spins forever, or edits that vanish when the connection returns. *Why:* Phones lose connection constantly; silent loss of work is the failure users forgive least. *Check:* With the network turned off, does every screen say so in one place, keep showing last data labelled as stale, and is no write silently lost? *See also:* single-status-location, consistent-save-model

## Accessibility

- **a11y-text-contrast**: Text has at least 4.5:1 contrast against its background (3:1 for large text), and icons, borders and focus rings that carry meaning have at least 3:1, in every theme. *Avoid:* Light grey helper text, brand colour on a brand tint, or placeholder-grey body text that passes in light mode and fails in dark mode. *Why:* Low contrast is the most common accessibility failure and hurts everyone outdoors or on a dim screen, not only people with low vision. *Check:* Does every text and meaningful graphic colour pair measure 4.5:1 (text) or 3:1 (large text, icons, borders) in both light and dark themes? *See also:* selected-vs-primary-color, dark-mode-checked-every-screen
- **a11y-keyboard-reachable**: Everything that can be tapped can also be reached and operated with the keyboard in a sensible order, with a visible focus ring at every stop; never remove focus outlines without replacing them. *Avoid:* outline: none, clickable divs with no key handler, custom dropdowns that Tab skips, and focus jumping to the top after an action. *Why:* Keyboard access is what screen readers, switch devices and power users all rely on, and it is cheap only when built in from the start. *Check:* Can you complete every flow with Tab, Shift+Tab, Enter, Space, arrows and Esc alone, with a visible focus ring at each stop and no keyboard trap? *See also:* a11y-focus-in-dialogs, selected-vs-primary-color
- **a11y-accessible-names**: Every control, link, form field and meaningful image has a text name a screen reader can say, describing what it does, not what it looks like; purely decorative images are hidden from assistive tech. *Avoid:* Icon-only buttons with no label, alt text of 'image.png', links that read 'click here', and the same label on buttons that do different things. *Why:* Without a name a screen reader says 'button', so the user cannot tell Delete from Save. *Check:* Does every control and meaningful image expose a name that says what it does, and are all decorative images hidden? *See also:* icon-only-secondary-on-narrow
- **a11y-focus-in-dialogs**: Dialogs and sheets move focus inside on open, keep it there while open, close on Esc, and return focus to the element that opened them; the page behind is inert. *Avoid:* A modal that opens while focus stays on the page behind, cannot be closed with Esc, and drops focus at the top of the page when it closes. *Why:* Keyboard and screen-reader users otherwise lose their place or interact with a page they cannot see. *Check:* On open, is focus inside the dialog; does Esc close it; on close, does focus return to the opener; is the background inert while it is open? *See also:* a11y-keyboard-reachable
- **a11y-semantic-structure**: Use native elements for their purpose (button, a, input, select, table, list), headings in order with one h1 per screen, and landmarks (header, nav, main, footer). *Avoid:* div with onClick for buttons, headings chosen for their font size, and tables built from floated divs. *Why:* Native elements give keyboard behaviour, names and roles for free; a correct outline lets screen-reader users jump to what they want. *Check:* With CSS turned off, does the page still read as a sensible outline, and is every interactive element a native control or has an explicit role and keyboard handler? *See also:* a11y-keyboard-reachable
- **a11y-not-colour-alone**: Never convey status, selection or validity by colour alone; add an icon, text or pattern. *Avoid:* Red and green dots as the only difference between failed and passed, or a selected tab shown only by a colour change. *Why:* About 1 in 12 men cannot tell red from green, and colour alone is also lost in greyscale screenshots and printouts. *Check:* In a greyscale screenshot, is every status, selection and error still distinguishable? *See also:* never-red-for-success, selected-state-tint
- **a11y-zoom-and-text-size**: Layouts survive 200% browser zoom and the largest system text size without loss of content or function; pinch zoom is never disabled. *Avoid:* user-scalable=no in the viewport tag, fixed-height containers that clip enlarged text, and px font sizes that ignore the system setting. *Why:* Many people enlarge text; a layout that only works at one size shuts them out. *Check:* At 200% zoom and with the largest system text size, is every control reachable and no text clipped or overlapping? *See also:* no-ellipsis-truncation, i18n-text-expansion
- **a11y-announce-changes**: Status changes that happen away from focus (toast, saving, async results, item counts) are announced through a live region, and form errors are linked to their fields. *Avoid:* A silent toast, a 'Saved' label that only changes colour, and an error summary that a screen reader never hears. *Why:* A screen-reader user cannot see a message appear elsewhere on the screen, so they do not know the action happened. *Check:* With a screen reader on, is every toast, save state and error announced once, politely, without stealing focus? *See also:* single-status-location, form-validation-timing

## Mobile and touch

- **touch-targets-and-spacing**: Every tappable control is at least 44 × 44 points (48 dp on Android) with enough space from its neighbours that a thumb cannot hit the wrong one; small visuals get a larger invisible hit area. *Avoid:* A 24-px icon with a 24-px hit area, adjacent icons with no gap, and tiny close buttons in the corner of a card. *Why:* Missed taps are the most common mobile complaint, and they are invisible in desktop testing. *Check:* Is every tappable control at least 44 × 44 with spacing from its neighbours, including icon buttons, list-row actions and dismiss controls? *See also:* icon-only-secondary-on-narrow, no-overlapping-inserters
- **thumb-zone-primary-actions**: On phones, the primary action and the most frequent controls sit in the lower part of the screen where a thumb reaches; destructive actions sit away from them; nothing important hides behind the keyboard. *Avoid:* A primary button in the top-right corner, Delete next to Save, and a submit button covered by the keyboard. *Why:* Most people hold a phone in one hand; what the thumb cannot reach gets used less and mis-tapped more. *Check:* With one hand on the smallest supported phone, can the primary action be reached without shifting grip, and is no destructive control adjacent to it? *See also:* sticky-save-bar-when-dirty, safe-areas-and-viewport
- **no-hover-only-interactions**: Nothing depends on hover: every hover-revealed control, tooltip or menu has a tap equivalent, and hover styles apply only where hover exists so a tapped button does not stay highlighted. *Avoid:* Row actions that appear on hover only, a tooltip as the only explanation of an icon, and buttons stuck in their hover colour after a tap on a phone. *Why:* Touch has no hover; what only hover reveals does not exist on a phone. *Check:* On a phone, is every hover-revealed control reachable by tap, and does no element stay in its hover state after being tapped? *See also:* hints-on-demand, a11y-accessible-names
- **safe-areas-and-viewport**: Respect the safe-area insets (notch, home indicator), size full-height layouts with the dynamic viewport rather than 100vh, keep input text at 16 px or more so the browser does not zoom on focus, and make sure the keyboard never covers the focused field or the submit button. *Avoid:* A bottom bar under the home indicator, a layout that jumps when the browser bar hides, a page that zooms in when a field is tapped, and a Save button hidden behind the keyboard. *Why:* These four problems are what makes a web app feel like 'a website in a browser' instead of a product. *Check:* On a notched phone with the keyboard open, is every control visible and tappable, with no content under the notch or home bar and no zoom on focus? *See also:* toast-never-covers-controls, thumb-zone-primary-actions
- **gestures-have-visible-alternative**: Every swipe, long-press or pinch action also has a visible control that does the same thing, and the gesture is hinted the first time. *Avoid:* Swipe-to-delete as the only way to delete, or a long-press menu nobody discovers. *Why:* Gestures are invisible; without a visible alternative they are undiscoverable for many and impossible for some. *Check:* Can every gesture-triggered action also be done through a visible control, and is the gesture taught once? *See also:* announce-new-features-once, handle-only-reorder, a11y-keyboard-reachable

## Dark mode and theming

- **theme-tokens-not-hardcoded**: Colours, shadows and elevation come only from semantic design tokens (background, surface, text, border, accent, success, warning, danger) that each have a light and a dark value; components never contain raw colour values; illustrations and shadows get dark variants. *Avoid:* #fff and #111 typed into components, a dark theme made with an invert filter, and drop shadows that vanish on a dark surface. *Why:* A hardcoded colour is a bug that appears only in the other theme, and there is no way to find them all except by grep. *Check:* Does a search of the components for raw colour values return zero results, and does every token have both a light and a dark value? *See also:* design-system-fonts-everywhere, dark-mode-checked-every-screen
- **dark-mode-checked-every-screen**: Dark mode follows the system setting by default, can be overridden and is remembered; higher surfaces are lighter, not shadowed; status colours are desaturated; every screen, dialog, toast, chart and embedded third-party widget is checked in dark mode with contrast re-measured. *Avoid:* Shipping a dark theme that was only seen on the home screen, pure white text on pure black, neon status colours, and a white third-party widget in the middle of a dark page. *Why:* Dark mode doubles the surface area to test, and the breakage hides in the screens nobody opened. *Check:* Has every screen (including dialogs, toasts, charts and third-party embeds) been viewed in dark mode, with text contrast re-measured and the choice remembered across visits? *See also:* a11y-text-contrast, theme-tokens-not-hardcoded, theme-applied-before-first-paint
- **theme-applied-before-first-paint**: Apply the chosen theme before the first paint (server hint or inline script), declare color-scheme so native controls, scrollbars and form fields match, and set theme-color per theme so the browser chrome matches too. *Avoid:* A white flash on every reload in dark mode, a bright white scrollbar and date picker inside a dark page. *Why:* A flash on every load makes a polished product feel cheap, and mismatched native controls look broken. *Check:* On refresh in dark mode is there no flash of the light theme, and do scrollbars, native pickers and the browser bar match the theme? *See also:* dark-mode-checked-every-screen, perf-fonts-no-reflow

## Motion and reduced motion

- **distinct-motion-styles**: Offer motion styles only if each is visibly distinct, with a live mini preview per style. *Avoid:* Presets or on/off switches that look nearly identical. *Why:* Near-identical presets were rejected; users wanted clearly different reveal styles. *Check:* Can a user tell every offered motion style apart from its preview?
- **motion-accessibility**: Reduced-motion users get no motion; long body text uses only a soft fade; any input finishes the reveal; animate only transform, opacity, clip-path and filter. *Avoid:* Decode or typewriter effects on paragraphs, ignoring reduced-motion. *Why:* Effects on long text hurt readability and performance. *Check:* Does reduced-motion disable reveals, and do paragraphs use only a soft fade?
- **decorative-motion-once**: Play decorative motion (a sheen, a shimmer) once on load and once per press, never on a loop, and not at all under reduced motion. *Avoid:* A shine that repeats forever on the primary button. *Why:* Looping decoration distracted from content and ignored people who asked for less motion. *Check:* Does every decorative animation have a finite iteration count and a prefers-reduced-motion off switch?
- **motion-explains-change**: Animate only to explain a change (where something came from or went, what is connected); keep UI transitions short (roughly 150 to 300 ms, exits faster than entrances, ease-out on entry); never block input while animating. *Avoid:* A 600 ms bounce on every panel, pages that cannot be tapped until the transition finishes, and animation added because it 'looks nice'. *Why:* Slow or decorative motion makes a product feel sluggish, and motion with no meaning is noise. *Check:* Does each animation explain a state change, finish within about 300 ms, and never delay the next tap? *See also:* motion-accessibility, decorative-motion-once, distinct-motion-styles
- **reduced-motion-is-global**: One global reduced-motion rule replaces movement (slide, scale, parallax, auto-playing video, looping decoration) with an instant or opacity-only change across the whole product; components do not opt in one by one; if motion is a product feature, add an in-app switch too. *Avoid:* Reduced motion handled in three components and forgotten in the other thirty, or a parallax hero that still scrolls under reduced motion. *Why:* Motion can cause nausea and distraction; a setting that only some components honour is worse than none, because people stop trusting it. *Check:* With the system reduce-motion setting on, does anything on any screen still move or auto-play? *See also:* motion-accessibility, decorative-motion-once
- **autoplay-is-muted-and-stoppable**: Anything that moves, blinks or plays by itself for more than five seconds can be paused or stopped by a visible control; auto-playing video is muted, shows a poster first, and does not start on a cellular connection without the user's choice. *Avoid:* An auto-playing hero video with sound, an infinite carousel with no pause, and a blinking badge. *Why:* Moving content competes with reading, triggers vestibular symptoms for some people, and burns mobile data. *Check:* Does every auto-playing or moving element longer than five seconds have a visible pause, start muted, and stay still under reduced motion? *See also:* reduced-motion-is-global, real-media-thumbnails, perf-images-and-media

## Visual system and media

- **real-media-thumbnails**: Media embeds show the real thumbnail with a play overlay. *Avoid:* Generic placeholder for embedded video. *Why:* Placeholder embeds made pages look broken and unfamiliar. *Check:* Does every media embed show its real thumbnail with a play overlay?
- **design-system-fonts-everywhere**: Every dialog, sheet and toast uses design-system fonts. *Avoid:* Sheets falling back to a different (e.g. serif) font. *Why:* A confirm sheet showed an unfamiliar font and users doubted the design system. *Check:* Do all dialogs and sheets use only design-system type tokens?

## Performance

- **perf-core-web-vitals-budget**: Set a performance budget per page and check it on every preview: Largest Contentful Paint under 2.5 s, Interaction to Next Paint under 200 ms, Cumulative Layout Shift under 0.1, measured on a mid-range phone over a slow connection; a change that breaks the budget does not merge. *Avoid:* Measuring only on a developer laptop over office Wi-Fi, or discovering slowness from user complaints. *Why:* Speed is a feature users notice first; without a budget every change is a little slower than the last. *Check:* Does the preview report LCP, INP and CLS for every key page on a throttled mid-range phone, and does CI fail when the budget is exceeded? *See also:* loading-without-layout-shift, perf-images-and-media, perf-ship-less-javascript
- **perf-images-and-media**: Images are sized to their slot, served in a modern format (AVIF or WebP) with responsive sizes, carry explicit width and height so space is reserved, and load lazily below the fold; video uses a poster and does not auto-download on cellular. *Avoid:* A 4 MB PNG scaled down with CSS, images without dimensions that push content around, and a 30 MB background video on mobile. *Why:* Images are the heaviest thing on most pages and the largest cause of both slow loads and layout shift. *Check:* Does every image have width and height, a modern format with responsive sizes, lazy loading below the fold, and is no image delivered at more than about twice its display size? *See also:* loading-without-layout-shift, real-media-thumbnails, autoplay-is-muted-and-stoppable
- **perf-fonts-no-reflow**: Self-host at most two type families, preload only the one or two files needed for the first screen, subset to the languages served, and use a fallback font tuned with size-adjust so text neither disappears nor jumps when the web font arrives. *Avoid:* Five weights from a third-party CDN, invisible text for two seconds, and a paragraph that reflows when the font loads. *Why:* Fonts block the first readable paint and are the second most common cause of layout shift. *Check:* Does text render immediately in a fallback and stay in place when the web font arrives, with only the first-screen font files preloaded? *See also:* design-system-fonts-everywhere, i18n-cjk-fonts-line-breaking, loading-without-layout-shift
- **perf-ship-less-javascript**: Split code by route, load third-party scripts only after the page is interactive and only where used, prefer platform features (native controls, CSS) over libraries, and give every third-party script an owner and a reason. *Avoid:* One bundle for the whole app, an analytics tag and a chat widget loading before the content, and a date library for one formatted date. *Why:* JavaScript is the most expensive byte: it must be downloaded, parsed and run, and it blocks taps while it runs. *Check:* Is the JavaScript loaded on the landing route within the budget, and does every third-party script have a named owner, a reason, and a deferred load? *See also:* perf-core-web-vitals-budget, loading-without-layout-shift
- **perf-respond-within-100ms**: Every tap gets visible feedback within 100 ms (pressed state, optimistic update, or a local change) even if the server takes longer; low-risk actions update optimistically and roll back with a message on failure; anything over about a second shows progress. *Avoid:* A like button that waits for the server before changing, a list that only re-renders when the response arrives, and a two-second wait with no indicator. *Why:* A product feels fast or slow based on the time to first feedback, not the time to completion. *Check:* Does every tap visibly respond within 100 ms, do low-risk actions update before the server replies, and does anything longer than a second show progress? *See also:* form-submit-once-with-feedback, loading-without-layout-shift, single-status-location

## Flows

- **external-setup-roundtrip**: Before sending users to an external setup step mid-flow (e.g. payment onboarding), auto-save, deep-link straight to the setup screen, and return them to the exact item they left. *Avoid:* Leaving through a generic settings/profile page and showing 'Leave without saving?' after the work was already saved. *Why:* A saved draft plus a detour and a false unsaved-changes warning made the flow feel broken. *Check:* After finishing external setup, is the user back on the same item with no unsaved warning? *See also:* consistent-save-model, preserve-scroll-highlight

## Status and feedback

- **single-status-location**: Show each status (progress, sync, error) in exactly one place on a screen. *Avoid:* The same upload progress rendered in a row and again in a banner or toast. *Why:* Duplicate progress indicators confused users about whether two uploads were running. *Check:* Is any state shown twice on the same screen?

## Payments

- **offline-payment-holds-expire**: Seats or stock held for manual/offline payment need an expiry, an organizer cancel action, and a per-buyer cap. *Avoid:* Unpaid holds that count against capacity indefinitely. *Why:* Unpaid holds blocked capacity forever and real buyers were turned away. *Check:* Do holds have an expiry, an organizer cancel, and a per-buyer cap? *See also:* catalog/payments.yaml
- **money-summary-integrity**: Money summaries subtract refunds once, exclude cancelled/expired orders from gross, store the processor's real fees, and label anything estimated. *Avoid:* Subtracting a refund from gross and again from net, or computing fees from a formula and showing them as fact. *Why:* A fully refunded order showed a negative net amount. *Check:* Does a fully refunded order show exactly $0 net, with estimates labelled? *See also:* catalog/payments.yaml
- **statement-descriptor-preflight**: Ask for the trading (DBA) name first and explain that the card statement descriptor must match the legal name or website before the processor validates it. *Avoid:* Letting users type any descriptor and surfacing the processor's rejection mid-setup. *Why:* Setup failed with an unexplained processor rejection error. *Check:* Does setup explain the descriptor rule before any error can occur? *See also:* catalog/payments.yaml
- **server-auth-redirect**: Redirect signed-out visitors from protected pages on the server with an HTTP 302 before any HTML is sent; the client check is only a fallback that shows nothing protected. *Avoid:* Serving the page, then checking the session in client script and redirecting. *Why:* The protected layout flashed before the redirect, which looked broken and briefly exposed private UI. *Check:* With no session, does a protected URL return a 302 to sign-in (safe same-origin return path) before any content loads? *See also:* single-status-location
- **one-toast-region**: Every global status message goes through one shared toast in one fixed place; only field-level errors stay next to their field. Success and info use a polite live region, errors an assertive one with a labelled dismiss button; errors are never pushed out by the display cap (they merge with a count); no toast motion under prefers-reduced-motion. *Avoid:* Each screen writing its own status text into its own inline spot, or a cap that silently drops the oldest error. *Why:* Messages appeared in many places, so people missed them and screen readers announced them inconsistently. *Check:* Is there exactly one toast component for global status (polite for success/info, assertive for errors, labelled dismiss, errors merged with a count instead of dropped, no motion under reduced-motion)? *See also:* single-status-location, toast-never-covers-controls

## Onboarding

- **public-support-address-not-home**: A public-facing support/business address must never default to the user's home address; warn that it is public and suggest a virtual or business address. *Avoid:* Prefilling the account's personal address into a field buyers can see. *Why:* Onboarding exposed a home address to buyers without the user realising. *Check:* Does onboarding warn that the support address is public and offer alternatives? *See also:* catalog/payments.yaml

## Privacy

- **agreement-snapshot-and-retention**: For agreements accepted at checkout, snapshot the exact text plus a hash per order, collect the minimum personal data (no IP unless required), scrub personal data when the stated retention ends, and update the privacy policy in the same change. *Avoid:* Linking to a live, editable agreement, logging IPs by default, and keeping data past the stated retention. *Why:* Personal data was kept beyond the retention period the policy promised. *Check:* Is data cleared at expiry, and does the privacy policy match what is collected and kept? *See also:* catalog/cross_border.yaml

## Engineering and release

- **clean-build-before-deploy**: Clear the build cache before a production build when design tokens or global CSS changed, then verify the deployed CSS. *Avoid:* Deploying from an incremental build whose cached CSS still held the old tokens. *Why:* A stale cache shipped old colours even though the source had changed. *Check:* Was the build cache cleared, and does the deployed CSS contain the new token values?
- **migration-numbers-by-merge-order**: When several branches add database migrations in parallel, assign migration numbers by planned merge order before review ends, and ship each migration to every environment's database. *Avoid:* Each branch picking the next free number on its own and assuming production migrates itself. *Why:* Three changes claimed the same migration number, and one never got its production migration. *Check:* Is there a merge-order table with unique numbers, and a migration applied for every database? *See also:* clean-build-before-deploy

## Responsive layout, site navigation and site content

- **desktop-is-not-a-stretched-phone**: Give wide screens their own layout: a capped frame, a hero band and two-column sections, while the phone layout stays unchanged. *Avoid:* One narrow mobile column centred in empty space on a laptop. *Why:* A phone column on a desktop made a business site look like an unfinished link page. *Check:* At 1440px, does the page use a frame wider than a phone column with text capped near 68 characters per line?
- **auto-layout-before-layout-controls**: Derive wide-screen arrangement from content order and length automatically; offer at most one escape hatch. *Avoid:* A grid builder asking users to place every block for each screen size. *Why:* Non-designers stall when asked to lay out the same page twice. *Check:* Can a user get a good desktop layout without touching any layout control?
- **reading-order-equals-visual-order**: Keep source, tab and screen-reader order identical to the visual order at every breakpoint. *Avoid:* Reordering columns with CSS so the screen order differs from the DOM. *Why:* Keyboard and screen-reader users jumped around the page unpredictably. *Check:* At each breakpoint, does tabbing move in the same order the eye reads?
- **nav-wraps-never-hides**: Let site navigation wrap to a second row, then switch to a labelled Menu button; never clip or silently hide items. *Avoid:* Nav labels cut with ellipsis or items pushed into an unlabelled overflow icon. *Why:* Visitors could not find pages whose links were cut off or hidden. *Check:* With a 60-character label, is every nav item fully visible or reachable from a labelled Menu? *See also:* no-ellipsis-truncation, collapse-long-nav
- **no-dead-nav-links**: Build navigation only from items that are currently public; skip anything private, unpublished or deleted at render time. *Avoid:* A menu that links to draft or removed pages. *Why:* Dead links in a header make a small business look closed. *Check:* Does unpublishing a page remove it from every menu without any extra step?
- **time-driven-content-updates-itself**: Lists driven by dates (upcoming items, next item) update with time on the server, with no republish. *Avoid:* Hand-maintained event lists that keep showing past dates. *Why:* Past events on a homepage made visitors doubt the business was active. *Check:* Does an item vanish from the list after its end time without anyone editing the page?
- **show-event-zone-not-viewer-zone**: Show event times in the event's own time zone with a short zone label when it differs from the viewer's. *Avoid:* Silently converting times to the viewer's zone or showing times with no zone. *Why:* Visitors travelling or out of town arrived at the wrong hour. *Check:* Does every displayed event time carry a zone label when the viewer's zone differs? *See also:* time-inputs-for-novices
- **designed-empty-states**: Every auto-filled module has a written empty state the owner can edit. *Avoid:* A blank gap or a heading with nothing under it when there is no data. *Why:* An empty section reads as a broken site. *Check:* With zero items, does the module show a short, editable message?
- **form-keeps-input-on-error**: On send failure, keep everything typed, show the error inline next to the action, and focus the first problem. *Avoid:* Clearing the form or showing a generic error page after a failed send. *Why:* Visitors who lose a long message rarely type it again. *Check:* After a simulated network error, is every typed character still there? *See also:* prevent-invalid-input
- **invisible-spam-protection-first**: Stop spam with invisible checks (managed challenge, honeypot, rate limit) before adding any visible puzzle. *Avoid:* A visible captcha on every contact form submit. *Why:* Visible puzzles cost real enquiries more than they save in spam. *Check:* Can a real visitor send a message without solving anything visible?
- **never-expose-owner-contact**: Deliver contact messages to the owner with the visitor as reply-to; never print the owner's address in the page. *Avoid:* A mailto link or address in the HTML of a contact block. *Why:* Published addresses get harvested and flooded with spam. *Check:* Is the owner's email absent from the page source? *See also:* agreement-snapshot-and-retention
- **maps-load-on-intent**: Show a static map and real address text; load an interactive map or third-party script only after a tap. *Avoid:* An embedded interactive map that loads on page view and traps scrolling on phones. *Why:* Map embeds slowed pages and hijacked scrolling on mobile. *Check:* Before any tap, are there zero third-party map requests and is the address selectable text?
- **paid-plans-unbranded-by-default**: When a plan includes removing platform branding, apply it automatically on upgrade and restore it on downgrade. *Avoid:* Requiring paying users to find a separate switch to remove a badge they paid to remove. *Why:* Paying customers kept the badge because they never found the setting. *Check:* After upgrading, is the badge gone with no extra action?

## Internationalization (i18n)

- **i18n-message-keys-day-one**: Products that may go multilingual must put all UI text behind message keys from day one and ban hardcoded strings via lint/CI. *Avoid:* Writing English UI strings directly in components and planning to 'translate later'. *Why:* Retrofitting hardcoded strings into translation files later is a large, error-prone sweep across every screen. *Check:* Does lint/CI fail on a hardcoded UI string, and is every visible string read from a message key? *See also:* elements/stack_comparisons.yaml#i18n
- **i18n-icu-plurals**: Write plurals, gender and selects as ICU MessageFormat inside the message, not as if/else in code. *Avoid:* count === 1 ? 'item' : 'items' in components. *Why:* Many languages have more than two plural forms (e.g. Russian, Arabic), and code-level branches cannot express them. *Check:* Is every count-dependent string an ICU plural message?
- **i18n-intl-formatting**: Format dates, times, numbers, currency and relative times with Intl APIs (or the i18n library's wrappers) using the active locale. *Avoid:* Hand-built date strings, fixed '$' symbols, toFixed(2) for money. *Why:* Order, separators, currency position and calendars differ per locale; hand formatting is wrong somewhere. *Check:* Is any date, number or price formatted without Intl or the library formatter?
- **i18n-no-concatenation**: Never build sentences by concatenating translated fragments; use one message with named placeholders. *Avoid:* t('hello') + ' ' + name + t('welcome_back'). *Why:* Word order differs by language (Japanese puts the verb last), so fragments cannot be reordered by translators. *Check:* Is any visible sentence assembled from more than one key or string piece?
- **i18n-text-expansion**: Design layouts to tolerate ~30-40% longer text (more for short labels) and wrapping; no fixed-width buttons or labels. *Avoid:* Pixel-fitted buttons and tabs sized to the English word. *Why:* German/French text is often 30%+ longer and short labels can double, which breaks or truncates layouts. *Check:* Does every screen still work with pseudo-localized text that is 40% longer? *See also:* no-ellipsis-truncation
- **i18n-cjk-fonts-line-breaking**: For CJK locales, set a per-locale font stack (subset or system fonts) and line-breaking rules (word-break / line-break: strict, or keep-all for Korean); check by eye. *Avoid:* One Latin web font for all locales and default breaking. *Why:* Missing glyphs fall back inconsistently (Han unification shows wrong regional glyphs) and lines break before punctuation or mid-word. *Check:* Has each CJK locale been checked by eye for font, glyphs and line breaks (lang attribute set)?
- **i18n-locale-fallback**: Define a locale fallback chain (e.g. zh-Hant-TW → zh-Hant → default) and a default locale; missing keys fall back, never show raw keys. *Avoid:* Showing 'checkout.title' to users when a translation is missing. *Why:* New keys always ship before all translations; without fallback, users see broken text. *Check:* Does a missing translation show the fallback language rather than the key?
- **i18n-key-naming**: Name keys by screen/feature and meaning (checkout.payButton), not by the English text; give translators context/descriptions. *Avoid:* Keys equal to the English sentence, or reusing one key for two meanings. *Why:* Text-as-key breaks when copy changes, and shared keys force one translation where languages need two. *Check:* Are keys namespaced by feature, unique in meaning, and described for translators?
- **i18n-ci-completeness**: CI checks every locale file has every key, no unused keys, and valid ICU syntax; release-blocking for shipped locales. *Avoid:* Finding missing translations from user reports. *Why:* Keys are added daily; only an automatic check keeps locales in sync. *Check:* Does CI fail when a shipped locale is missing a key or has broken ICU syntax?
- **i18n-pseudo-localization**: Run a pseudo-locale (accented, ~40% longer, bracketed text) in dev/QA before real translations exist. *Avoid:* Waiting for real translations to find hardcoded strings and clipped layouts. *Why:* Pseudo-localization exposes hardcoded strings, concatenation and overflow on day one at zero cost. *Check:* Can the app be switched to a pseudo-locale, and has every screen been viewed in it?
- **i18n-locale-switcher-and-detection**: Pick the first locale from the user's account setting, then the URL, then the browser language; show a visible switcher that lists languages in their own names (日本語, not Japanese); remember the choice; put the locale in the URL of public pages so each language can be indexed. *Avoid:* Locale guessed from IP address, a switcher hidden in account settings listing 'Japanese' in English, and one URL for every language. *Why:* People travel and share devices; a wrong locale they cannot find how to change is a lost user, and un-indexed translations bring no traffic. *Check:* Can a user find and change the language from any screen in one step, is the choice remembered, and does each public page have a per-locale URL? *See also:* i18n-locale-fallback, plain-localized-terms
- **i18n-rtl-and-logical-properties**: If a right-to-left language may ever be served, use CSS logical properties (inline-start and inline-end instead of left and right), set dir on the document, mirror directional icons (back, next, progress) and keep numbers, phone numbers and code left-to-right. *Avoid:* margin-left everywhere, a back arrow that points the wrong way in Arabic, and a progress bar that fills from the wrong side. *Why:* Retrofitting direction into hundreds of left and right declarations is as painful as retrofitting message keys. *Check:* Does switching to a right-to-left locale mirror the layout and directional icons with no overlapping text, while numbers stay left-to-right? *See also:* i18n-message-keys-day-one, i18n-text-expansion

## Design system and agent handoff

- **component-map-only**: UI-building agents use only tokens and components in the product's component map (`reference/component-map-template.md`, copied into the repo and linked from AGENTS.md). *Avoid:* inventing hex values or near-duplicate components. *Why:* Raw values and duplicate components accumulate and the visuals drift. *Check:* Does every colour, spacing value and component come from the map (or is a map update in the same PR)?
- **learn-from-rejection**: When PR review requests a UI fix, feed it back into the component map or a rule. *Avoid:* fixing the same comment by hand each PR. *Why:* Fixes that never reach the map get repeated by the next agent. *Check:* Was the map or a rule updated, or a `component_map_update` learning proposed?
- **capsule-handoff**: Hand features to agents as a one-page capsule (`reference/capsule-template.md`); the agent replies with a draft PR. *Avoid:* one-line chat requests. *Why:* Without a fixed spec the agent guesses scope and states. *Check:* Is every capsule section filled before the agent starts?
- **preview-state-switcher**: Preview builds have a state switcher (device, theme, signed-in/out, role, empty/loading/error), compiled out of production. Sign-in/role switching only changes the displayed UI via mock data or test accounts; it cannot change server-side permissions. *Avoid:* reviewing only the happy path, or shipping the panel. *Why:* Reviews only see the happy path, so other-state breakage reaches production. *Check:* Can every state be switched in preview with mock data/test accounts only, and is the panel removed at build time (tree-shaken/compiled out — a runtime flag that merely hides it is not enough)?
- **annotation-to-fix** (optional): Send review notes as structured items — file + component, instruction, global direction (`reference/annotation-to-fix-example.md`). *Avoid:* vague screenshot comments. *Why:* Without location and direction the agent fixes the wrong place. *Check:* Does each note name file, component and instruction?
- **generative-ui-within-schema**: In-app AI-generated UI uses only components/tokens/config allowed by a schema derived from the map, validated before display — components, text and URLs alike. *Avoid:* free HTML/CSS from a model shown directly. *Why:* Free generation produces off-design or broken output. *Check:* Is output validated against the schema, with max text lengths, javascript:/data: links rejected, no raw HTML rendered, and a safe fallback?


## Phase gates (one yes/no per lifecycle stage)

Gates live in `phase_gate_checks` of `catalog/ui_ux.yaml` (Japanese, with the rule ids each gate bundles). `lifecycle` is one of idea, launch, operate, scale, exit; the MCP tool `ui_ux_checklist` takes it as a filter. Summary in English:

- **gate.i18n_keys** (idea): Right after the languages to serve are decided, before the first screen: if there is any chance of more than one language, UI text goes behind message keys and hardcoded strings fail lint/CI (if zero chance, record why).
- **gate.ux_targets_idea** (idea): In requirements, before the first screen: write down the accessibility target (WCAG 2.2 AA), supported devices and minimum width, dark mode yes/no, reduced-motion support, and the performance budget (LCP 2.5 s, INP 200 ms, CLS 0.1). *Rules:* a11y-text-contrast, a11y-keyboard-reachable, touch-targets-and-spacing, dark-mode-checked-every-screen, reduced-motion-is-global, perf-core-web-vitals-budget
- **gate.screen_state_matrix** (idea): In requirements, before design: a screen × state matrix lists loading, empty (first use), empty (no results), error, offline, 1 item and many items for every screen, and who can see each. *Rules:* define-every-screen-state, empty-state-teaches-next-step, error-state-recoverable, offline-and-stale-shown-once
- **gate.a11y_launch** (launch): Before going public: every main flow completed with the keyboard alone, one flow with a screen reader, contrast measured on every screen, and the findings fixed. *Rules:* a11y-keyboard-reachable, a11y-accessible-names, a11y-focus-in-dialogs, a11y-text-contrast, a11y-not-colour-alone, a11y-zoom-and-text-size, a11y-announce-changes
- **gate.states_devices_launch** (launch): Before going public: on real iOS and Android devices at the smallest supported width, every screen seen in each state, in dark mode, under reduced motion and in the pseudo-locale. *Rules:* define-every-screen-state, dark-mode-checked-every-screen, reduced-motion-is-global, safe-areas-and-viewport, touch-targets-and-spacing, i18n-pseudo-localization
- **gate.perf_launch** (launch): Before going public: LCP, INP and CLS of the key pages measured on a mid-range phone over a slow connection and within budget, with CI failing when the budget is exceeded. *Rules:* perf-core-web-vitals-budget, perf-images-and-media, perf-fonts-no-reflow, perf-ship-less-javascript, theme-applied-before-first-paint
- **gate.ux_signals_operate** (operate): Monthly while operating: error rate, drop-off and support tickets per screen, real-user Core Web Vitals and automated accessibility checks reviewed; each fix written back into a rule or the component map. *Rules:* perf-core-web-vitals-budget, error-state-recoverable, single-status-location, announce-new-features-once
- **gate.ux_scale** (scale): Before adding languages, devices, audiences or data volume: lists, search and loading checked with 10,000 items; the new locale checked in the pseudo-locale and RTL; new widths checked; tokens and components still have a single source. *Rules:* define-every-screen-state, perf-ship-less-javascript, perf-respond-within-100ms, i18n-text-expansion, i18n-rtl-and-logical-properties, i18n-locale-switcher-and-detection, theme-tokens-not-hardcoded
- **gate.ux_handover_exit** (exit): Before handing over or selling: design tokens, component inventory, screen × state matrix, glossary, accessibility conformance record, UX metric history and known-issues list are in the repository so a buyer or successor can rebuild the screens without any external tool. *Rules:* theme-tokens-not-hardcoded, one-term-per-concept, define-every-screen-state, design-system-fonts-everywhere
- **gate.component_map** (idea): Before the first screen: the component map is in the repository and linked from AGENTS.md. *Rules:* component-map-only
- **gate.state_switcher_design** (idea): Design: a preview state switcher (device, theme, signed-in/out, role, empty/loading/error) exists, driven by mock data or test accounts only. *Rules:* preview-state-switcher
- **gate.state_switcher_review** (launch): Review: every listed state was checked in the switcher. *Rules:* preview-state-switcher, define-every-screen-state
- **gate.state_switcher_release** (launch): Before going public: the switcher is compiled out of the production bundle (not merely hidden by a runtime flag). *Rules:* preview-state-switcher
- **gate.learn_from_rejection** (operate): On every review-requested UI fix: the component map or a rule was updated, or a component_map_update learning proposed. *Rules:* learn-from-rejection
